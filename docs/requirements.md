# 要件: X のネタ元アカウント探しの改善

2026-10-05 に、コードを見ずに整理した結果（1段階目）。2026-10-06 に今のコードと突き合わせ、その結果と決定を反映した（2段階目）。2026-10-07 に 1・2 を作り、実データを見て 3・4 を保留にし、5 を先に作ることにした。

## 目的

X のリストに入れて引用・発信するための、良いアカウントを、少数だけ・新しい人中心に・手間なく見つけたい。

今の不満:
- 数が多すぎて、全部は見られない（選ぶのにも時間がかかる）
- 毎週同じ人が出てきて、新しい人がわからない
- 発信していない人や、AI と関係ない投稿ばかりの人が混ざる
- 毎回手で実行するのが面倒

## 決めたこと

当初は「自動化は最後」（一覧の中身が良くなる前に自動化しても、良くない一覧が毎週届くだけなので）としていた。1・2 を作って実データで動かすと、今週の新しい人は2人だけで、絞り込みが必要なほど多くなかった。そこで 3・4 を保留にし、5 を先に作る。

### 3・4 に戻る条件

5 で届く通知を3〜4週間見てから判断する。3 は、通知を見て作るかどうかを決める。4 は、人数が多すぎると感じたら戻る。それまで X の API の準備（開発者アカウント、従量課金、トークン）はしない。

1. **新しい人だけ**: 先週までに一覧に出た人と、X の判定で落ちた人を除く。人は GitHub の login で見分ける（X のハンドルは変えられるため）。
2. **少数に絞る**: GitHub のフォロワー数が多い順に並べ、上位 N 人だけを出す（N は既定 10、実行時に変えられる）。
3. **（保留）メジャーな AI 組織の人に印を付けて優先する**: AI 組織の人を先に並べ、そのあとをフォロワー順にする（2 の並びの中で優先する）。
   対象は Anthropic、OpenAI、Google DeepMind、Meta、Hugging Face、Mistral AI。判定は GitHub プロフィールの所属（company）と、その組織の公開メンバーかどうか。
4. **（保留）X で AI について発信している人だけにする**: X の API で直近20件の投稿を読み、AI に関する投稿が3件以上ある人だけを残す（発信していない人を除く）。X のフォロワー数も併記する。予算は月1,000円程度。
   - 予算を守るため、X の判定は上位 N 人だけに行う。判定で落ちた人の分は、N 人目より下の人で補充しない（一覧が N 人より少なくなってもよい）。
   - 判定で落ちた人も記録し、翌週から除外する（1）。
   - 月の読み取りは 1,600件を上限にし、読む前に判定する。今回読む予定の件数をその月の件数に足すと 1,600件を超えるなら、その回は X の判定をせず、2・3 までの一覧だけを通知する。
5. **毎週自動で実行する**: GitHub Actions で毎週決まった時間に実行し、一覧を自分に通知する。リポジトリへのコミットや Issue にはしない（Issue は放置されて溜まるため）。
   - 通知は Discord の Webhook で自分に送る。Webhook の URL は GitHub の Secrets に `DISCORD_WEBHOOK_URL` として置く。
   - 記録は GitHub Actions の artifact に JSON ファイル1つで残す。中身は login ごとの初出の週と判定結果（一覧に出た・X の判定で落ちた）、月ごとの X の読み取り件数。4 を保留している間は、今の形（`{"first_seen": {"<login>": "<週>"}}`）の初出の週だけを受け渡す。毎回、前回の成功した実行の artifact を取ってきて更新し、また artifact として残す。
   - 公開リポジトリの定期実行は、60日間リポジトリに動きがないと止まる。対策は入れず、止まったら手で再開する。

## 後回し（1〜5 のあとに判断する）

- **トップコントリビューターを引用している X の発信者**も候補に入れる。X の検索 API が必要で、情報源を広げる別の機能になるため。
- **X のリストへの自動追加**。最終的に人間が選ぶので、まずは一覧で十分。

## 作らないこと

- 「これから伸びそうなベンチャー」の機械的な判定。基準を数値にできない。AI 系の trending 自体がすでにその候補を拾っているので、そこに任せる。

## 置いた仮定

- 上位の人数 N は既定 10 人。「何人でもいいが、多すぎると管理と選ぶ手間が大変」という答えから。
- 「先週までに出た人」は、過去の実行結果を保存して判定する（保存先は 5 の artifact）。
- 「AI に関する投稿」は、投稿の本文にキーワード（AI、LLM、GPT、Claude、Gemini、model、agent、機械学習、生成AI など）が含まれるかで判定する。費用をかけずに始めるため。
- 4 の X の投稿の読み取り量は、月あたり 上位 N 人 × 20件 × 約4回（N=10 なら約800件）。
- X の API は従量課金を想定する。読み取り 1件 約0.005ドル（X の公式の料金で要確認）。N=10 なら月約800件で約4ドル（約600円）の見込み。
- 週1回の実行なので、月に5回実行する月がある（N=10 なら約1,000件）。
- 英語・日本語どちらの発信者でもよい。

## 今のコードとの突き合わせ（2026-10-06）

関係するのは `core/github_contributors.py` とそのテストだけ。LangGraph の日次パイプライン（`main.py`、`scripts/run_daily.sh`）とは別の機能。

### すでにあるもの

- 今週の AI 系 trending から候補を集める処理（`collect_weekly_ai_trending_x_accounts`）。trending ページを読み、topics に `ai` か `llm` があるリポジトリの上位3人のうち、X のアカウントがある人を重複なしで出す。
- GitHub の認証（`github_api_request` が `GITHUB_TOKEN` を付ける）。Actions の自動 `GITHUB_TOKEN` をそのまま使える。
- 2・3 の材料の一部。毎人呼んでいる `GET /users/{login}` の返り値に `followers` と `company` が入っている（今は `twitter_username` しか使っていない）。
- 標準ライブラリだけで動くので、Actions で依存を入れなくても実行できる。

### ぶつかるもの（決定済み）

- 今の関数は Markdown の行をつないだ文字列だけを返し、フォロワー数や所属を持たない。既存の関数は変えず、レコードの一覧を返す新しい関数を足す。
- X の判定で落ちた人を記録しないと、毎週読み直されて予算と枠を使い続ける → 落ちた人も記録して除外する（1・4）。
- 月の上限には実行をまたいだ件数の記録が要る → 記録の保存先で一緒に持つ（5）。上限は読む前に判定する（4）。
- 3 の「優先する」と 2 の並びの関係 → AI 組織の人を先に並べる（3）。
- `spec.json` の「作らないこと」に「X API を使ったフォロワー数取得」があるが、この文書を正とする。

### 作るのに大きな手間がかかるもの

- **X の API**: 開発者アカウント、従量課金の設定、トークンの発行は手作業。X の認証用の Secret（例: `X_BEARER_TOKEN`）がもう1つ要る。ハンドルから X のユーザーを引く呼び出し（フォロワー数もここで取る）が1人1回増え、これが課金されるかは要確認。
- **GitHub Actions**: `.github/workflows/` はまだないので、ゼロから作る。記録の artifact の取得と保存もここで行う。
- **AI 組織の判定**: 公開メンバーかどうかは `GET /users/{login}/orgs` を1人1回足せば取れる。手間は名前の対応づけ（特に Meta は `meta-llama`、`facebookresearch`、`facebook` などに分かれ、`company` 欄の書き方もばらばら）。
- Discord の通知は小さい（標準ライブラリで JSON を POST するだけ）。

### artifact を選んだ理由と受け入れる点

- キャッシュは7日間使われないと消え、週1回の実行が少し遅れるだけで記録が消える。別ブランチはコミットしない方針とぶつかる。Variables や別の非公開リポジトリは個人のトークン（PAT）が要る。artifact は追加の Secret もコミットも要らない。
- 公開リポジトリの artifact は、ログインした人なら誰でも取れる。中身は GitHub の login、X のハンドル、月の件数で、どれも元から公開されている情報。
- artifact は90日で消える。実行の失敗が続いて90日を超えると記録は空から始まり、全員が「新しい人」に戻る。
