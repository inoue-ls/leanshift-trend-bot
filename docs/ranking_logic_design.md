# トレンドニュース順位付けアルゴリズム設計書 (ranking_logic_design)

本書は、4ソースから収集した計12件のテックニュースを、ユーザーの関心情報（`my_status.txt`）をベースに順位付け（1位から12位）するための、スコアリング比率の決定根拠およびエッジケースに対する対処方針を定義するドキュメントです。

---

## 1. スコアリング基準と比率設計の根拠

ニュースの総合評価値（100点満点）は、以下の3つの評価軸に基づいて加重平均で算出されます。

```
総合スコア = (ユーザー関心度 × 0.5) + (ビジネス・技術価値 × 0.3) + (新規性・トレンド性 × 0.2)
```

| 評価軸 | 比重 | 役割・選定根拠 | スコアリング目安 |
| :--- | :---: | :--- | :--- |
| **ユーザー関心度**<br>(User Interests) | **50%** | **【最重要フィルター】**<br>情報過多を防ぎ、ユーザーにとって「今読むべき情報」を最上位に配置するための軸。`my_status.txt` の内容と直接的・間接的な関連度を測る。 | **5点**: キーワードと完全一致または極めて密接<br>**3点**: 関連する周辺技術や同ジャンル<br>**1点**: 全く無関係 |
| **ビジネス・技術価値**<br>(Business & Tech Value) | **30%** | **【実用性・適用可能性】**<br>単なる話題性だけでなく、日本市場向けローカライズビジネスのタネになるか、開発効率を上げる画期的なツールかという「価値の実体」を評価する軸。 | **5点**: 産業・開発プロセスを激変させる影響力<br>**3点**: 便利なアップデート、有用な新規ツール<br>**1点**: 局所的なニュース、個人のブログ記事等 |
| **新規性・トレンド性**<br>(Novelty & Timeliness) | **20%** | **【情報の新鮮さ】**<br>同じような解説記事や競合ツールを排除し、「今まさに登場した新しい情報」を優遇するための軸。 | **5点**: 初回ローンチ、画期的な新技術の初公開<br>**3点**: メジャーアップデート、認知度上昇中<br>**1点**: 既存技術の解説、古いニュースの再掲 |

### 比率決定の意図
- **50% (ユーザー関心度)** に設定することで、「世間的にはそこまで話題ではないが、自分にとっては超重要」なニュースがしっかり上位に浮上します。
- **30% (ビジネス・技術価値) と 20% (新規性)** は、関心度が同率（または関心度ゼロ）のニュースを並べる際の「客観的フィルター」として機能し、レポートとしての質と有用性を保証します。

## 2. エッジケースにおける対処方針（LLM 制御ロジック）

Gemini が 12 件の記事を処理する際、実環境では様々な入力データのエッジケース（極端なケース）が発生します。これらに対し、ハルシネーションや不整合を起こさず美しく処理するためのプロンプト指示および実装方針を定義します。

### Case 1: 関心トピックが全記事に一致しない場合（一致率0%）
- **事象**: `my_status.txt` が「音楽生成AI」だが、本日の12件は「インフラ、Rust、フロントエンド」のみで、関連記事が1件もない。
- **対処方針（フォールバック）**:
  1. ユーザー関心度スコアはすべて「1点（最低点）」として評価します。
  2. 順位付けの決定権は自動的に**「ビジネス・技術価値（比重60%）」と「新規性（比重40%）」にシフト**します。
  3. 各記事の `evaluation_reason` には、「今回、直接的な関心トピックに関連する記事はありませんでしたが、ビジネス価値と新規性の観点から〇〇として評価しました」という旨を明記させます。

### Case 2: 逆に関心トピックがすべての記事に一致する場合（一致率100%）
- **事象**: `my_status.txt` が「AI」で、12件の記事がすべて何かしらの AI 関連ニュースである。
- **対処方針（タイブレーク）**:
  1. ユーザー関心度スコアはすべて満点となります。
  2. この場合、残りの50%である「ビジネス・技術価値」と「新規性」のスコア差によって厳密に順位が決定されます。
  3. 単に「AIだから」という理由だけでなく、「そのAI技術がどれほど画期的か（新規性）」「ビジネスにどう繋がるか（価値）」の対比を `evaluation_reason` で明確に説明させます。

### Case 3: 関心トピックが極端に抽象的、または狭すぎる場合
- **事象**: 関心事が「テクノロジー」のように広すぎる、あるいは「Next.js 15.0.3 の App Router」のようにピンポイントすぎる。
- **対処方針（意味拡張）**:
  - プロンプトの役割定義で「セマンティック拡張（意味の類似性評価）」を許可します。
  - **抽象的すぎる場合**: 一般的なテックの中でも「開発ツール」「AI」「SaaS」など、12記事中の相対的に最も価値の高いものを自動選択します。
  - **狭すぎる場合**: 近似概念（Next.js であれば React、Vercel、SSR、フロントエンド全般）までスコアリング対象として含め、関連度3点（周辺技術）として処理します。

### Case 4: 同一ニュースや極めて類似した記事が重複している場合
- **事象**: Hacker News と TechCrunch の双方で「Next.js 15 RC リリース」が取得され、12件中に同じ内容の記事が複数存在する。
- **対処方針（デデュプリケーション / 排他順位）**:
  1. 内容が重複している記事がある場合、より情報量が豊富（サマリーが詳しい、または信頼性が高いソース）な方を上位に位置づけます。
  2. 重複したもう一方の記事は、順位を大幅に下げるか、「重複した既知情報」としてスコアを減点させます。
  3. 評価理由に「重複記事であるため、より詳細な情報源であるID: 〇〇を優先し、こちらは順位を下げました」と記載させます。

## 3. Gemini 2.0 Flash における安定評価の設計ルール

これら複雑なロジックを Gemini 2.0 Flash に狂いなく処理させるため、APIコール側では以下のパラメータ設定を行います。

1. **低い Temperature (温度) の設定**:
   - `temperature=0.1` 〜 `0.2` を強く推奨します。クリエイティブさ（揺らぎ）を抑え、スコアリングと順位決定の論理的整合性を最優先させます。
2. **システムプロンプトでの「評価理由」の強制（CoT効果）**:
   - 出力構造の中で、`evaluation_reason`（評価理由）の項目を `one_line_summary` や `x_draft` よりも**前（左側）に配置**します。LLMはトークンを左から右へ生成するため、評価理由を先に書かせる（思考させる）ことで、その後に続く出力データがより論理的かつ高品質になります。
